# 五小时内的动态优先验证

## 截止与目标

北京时间2026-11-28约08:20接到五小时要求，执行截止固定为当日13:20（不因部署耗时顺延）。
保留A→B→A单一动态场景，优先形成真实同预算对照及模块消融，不引入TPC-C、JOB，不生成文献比例伪实测曲线。

## 执行顺序

1. 等待已启动的修复版开发种子43结束并通过恢复/数据校验；失败则停止新付费运行。
2. 新请求种子44，依次执行Default、AgenticDB（DB-only）、AgentTune、ADMTune。
3. 同一种子44，依次执行ADMTune的no_history、no_gp、single_slice、no_reflection。
4. 每完成一项保存指标、状态和公开数据包；四方法齐全后自动生成主图，消融有完整结果后追加消融图。

本批次只有每方法一次，不宣称多种子显著性。开发种子43不并入新种子44主图，不用修复前旧版本抵充新版重复。顺序固定是本轮时间受限的限制，不能消除机器随时间漂移；后续独立重复应轮换顺序。

## 共同协议及资源

- 沿用dynamic_matrix_v1：每阶段600秒、10 QPS、四工作线程、每阶段6000请求，共18000请求。
- 四表各200万行，range-mixed查询，A/B为9:1/1:9扫描排序组成，A重现恢复9:1。
- 独立冷重启、180秒中性预热、不清OS页缓存，每次测量15秒预热＋60秒测量。
- 相同四参数目录、原阶段检测及安全约束，不调整GP门槛以制造收益。
- 每个调优运行最多18试验槽（含失败）、36次LLM请求、100000 token。
- 若全部七个调优运行完成，新增上限252次LLM请求、700000 token；这是上限而非消费目标，不包含此前已启动的开发验证。Default与绘图不调用LLM。

## 停止与交付

- 只有剩余至少45分钟才启动下一项，给完整运行、恢复和绘图留余量；不为了赶时间缩短协议。
- 不按性能胜负决定是否保留；任何执行或恢复失败均留档并停止队列，不无限重试。
- 若异常运行临近截止，发送中断让执行器尝试finally恢复，预留恢复检查时间。无法保证任意操作系统/API故障下进程一定及时结束；未确认恢复前不得启动其他任务。
- 状态为completed表示八项均完成；budget_stopped表示只完成了其中一部分，未启动项目不能计作已验证。
- 服务器后台运行，SSH断开不应终止任务；服务器停机会影响运行。当前不是自动重启后无损续跑系统。
- 输出：动态过程、全程/分阶段P95、达标耗时、成功请求数、真实试验槽、LLM调用/token；无历史复用重点看A2。
- no_reflection检验文字反思通路，不能代替增量与全历史反思的质量/费用比较。

入口为`python -m tools.run_priority_dynamic`。该脚本仅编排已有冻结实验并离线绘图，不修改核心调优算法。
