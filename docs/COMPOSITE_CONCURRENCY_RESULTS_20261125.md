## 2. 预先固定的综合评估目标

本轮评估目标为同次观测的 **TPS / P95(ms)，越大越好**，标识 `tps_per_p95:maximize`。仍保留TPS、平均延迟及P95。

执行适配器仍返回原始TPS，综合分数另存 `joint_value`，没有假称原纯TPS运行已经按综合指标优化，也没有将固定1000 TPS延迟与最大吞吐拼接。**当前仅完成综合指标下的手工配置诊断，尚未接通综合目标的付费GP/LLM搜索闭环。**

没有业务硬SLO，因此没有凭空加入20%相对延迟阈值；执行器既有1000 ms P95运行保护仍保留，本轮9次均未触发。这不是新设的业务SLO，也不是综合分数等同于SLO保证。

## 5. 因果解释与恢复

- 并发8相对BufferOnly的三个区组综合分数差值均为正，P95下降约6.96%—10.25%，属于有限的改善证据；三次技术重复不足以宣称统计显著、全取值最优或算法优势。
- **并发8仍约98.52%的CPU配额周期发生节流，容器CPU约11.87核，未从根本上解除12核配额下的饱和。** 8个InnoDB并发限制不能直接理解为容器只消耗8核，它也不控制所有MySQL执行、客户端和其他CPU活动。官方变量语义见MySQL 8.0 Reference Manual §17.8.4。
- 只有Concurrency8的正式边界 `innodb_thread_sleep_delay` 为0，其他两组为10000；它在并发8的预热期已发生引擎自适应调整，不能假称测量期间所有并发上下文始终相同。`innodb_adaptive_max_sleep_delay=150000`、事务票据5000保持不变。每次前后及最终均在恢复并发0之后将上下文复位到初始读值并校验，防止该自适应状态悄悄带入下一条。
- 因而本轮观察的是该数据库参数与其原生自适应机制共同产生的结果，不是隔离出“CPU少了4核”的实验，也不是改变OS配额的实验。
- Default的综合分数仍最高；新增并发8不是已解决尾延迟问题的配置，不追加更多取值直至获胜，也不覆盖此前最大吞吐记录。

## 6. 下一步必须转向方法而非继续手工挑参数

1. 在新协议中将同次TPS/P95真正接入GP标签、候选排序、配置接受和反思反馈，并保留原始TPS/P95字段。旧纯TPS和固定速率数据不能不加协议过滤地当成新目标标签。
2. 修复“所有候选被代理拒绝后长期重复最优配置”的路径：有预算时进行有限次数的新候选刷新；仍无新候选时明确提前停止，预留最终复测，不用重复填满100分钟。
3. 用离线回归和小预算真实LLM联调验证上述修改，之后才做同协议Default、AgenticDB数据库层变体、AgentTune等正式对比。
4. 动态负载、历史复用、代理预筛、增量反思的价值仍需独立消融与多种子验证；当前手工探针不是算法消融，不能据此宣布ADMTune胜过其他方法。
