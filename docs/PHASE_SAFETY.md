# 阶段时长不兼容的原因与保护机制

受控实机验收已通过，原始记录和 CSV 双份保存，详见 [2026-11-23 验收记录](PHASE_GUARD_20261123.md)。

## 根因

1. 原来的 24 秒阶段是动态监测烟测协议，并未承诺能完成参数优化。
2. 当前实机静态协议是 15 秒预热加 60 秒测量；这 75 秒还不含配置应用、结果封存和恢复。公开示例则是 30 秒预热加 120 秒测量，不能混淆。
3. `Ledger` 原先只管理全局时间与次数，不检查某个负载阶段剩余时间。
4. 静态 `Controller` 同步执行测量是正常行为，但不能直接在持续请求调度回调里调用它，否则阻塞到达调度；历史窗口本身也不能保证长测量未跨阶段。
5. 低速单 SQL 回放和 Sysbench OLTP 是不同协议，后者还会注入额外请求。不能把静态 TPS 直接标记为动态回放的性能。

## 修复一：预算先行，而不是缩短测量

`PhaseTiming` 从指定 benchmark 文件读取预热和测量时长，计算：

```text
检测预留 = (变化确认窗数 + 稳定观察窗数) × 窗长
单试验预留 = 配置应用 + 预热 + 测量 + 一个封存窗口 + 恢复
阶段最小时长 = 向上对齐到完整窗口(检测预留 + 阶段提案预留 + 试验数 × 单试验预留)
```

默认假设窗长 4 秒、确认与稳定各两窗、应用/恢复各 15 秒、每阶段提案预留 30 秒：

| 输入协议 | 每阶段试验槽 | 阶段最小时长 |
|---|---:|---:|
| 当前实机 15+60 秒 | 5 | 592 秒 |
| 当前实机 15+60 秒 | 8 | 920 秒 |
| 公开示例 30+120 秒 | 5 | 968 秒 |

槽数包括基准、启动探测、候选和复测，不能把复测排除在预算之外。五槽示例不包含额外三个“免费复测”。

这些是**显式预算假设，不是实测校准结果或硬实时保证**。检测预留假设切换对齐窗口且新阶段平稳；随机波动可能更晚稳定。迟到时减少可用试验数，不能延长预定阶段来容纳某个方法。

需要重启的参数不能沿用默认 15 秒应用预留，应按执行器的重启等待与恢复需求增大预算。装饰器要求阶段单试验预留不小于执行器的时长估计，预算不匹配直接拒绝构造。

不访问数据库或模型即可规划；`--output` 不能覆盖已有文件：

```sh
python -m admtune.phase_safety \
  --benchmark configs/local/autodl-smoke-benchmark.yaml \
  --trials-per-phase 5 --phase-seconds 600 \
  --output runs/phase-plan-001.json
```

使用公开 benchmark 时应按其 150 秒协议重新规划，例如五槽、1000 秒阶段。不能用本表中 75 秒协议的数字套用所有 benchmark。

## 修复二：阶段级准入

`PhaseFence.start()` 只允许在近期完整窗口确认稳定、阶段编号和上下文匹配时发起观测。对公告的实验阶段边界，检查剩余时间是否包含整个试验、封存与恢复预算；同时限制阶段试验槽，失败不退还槽数。

没有公告未来切换的线上负载不使用未来边界作输入；只能依赖运行时观测栅栏和全局预算。公告边界不进入负载检测特征或候选收益推断。正式对比要让各方法获得相同的时间信息，或统一仅用于事后剔除混合观测。

有限窗口不能证明窗口内从未发生过未被检测的变化。因此对未知线上边界，栅栏只保证“已观察到异常的在途测量不被接受”，不提供物理负载恒定的数学保证。本次受控验收另用公告边界事后审核跨段情况。

## 修复三：测完不立即成为标签

观测从 provisional 开始，只有覆盖其终点的完整窗口到达后才能封存：

- 变化怀疑即作废在途观测，不必等第二窗正式确认。
- 窗口丢失、长度异常、阶段 epoch 改变或监测结束，都拒绝未封存观测。
- 真正的执行器必须回报实际结束时刻；超出预计时间时等待更晚的完整窗口，不能提前封存。
- 公告截止时间超支、封存等待超时均失败关闭，不产生有效性能值。
- 已经封存的历史观测不会因为后续正常切换而被删除。

`PhaseGuardedExecutor` 是提供给独立调优线程的装饰器：监测继续推进栅栏，调优线程等待封存。失效结果返回 `value=None`、`complete=false`，不满足现有 `Trial.trainable` 条件。准入拒绝没有改配置时，不调用不存在的恢复快照；实际执行过的恢复仍委托原执行器。

装饰器核对执行器与被监测负载的协议标识。现有 `AgenticDBExecutor` 明确是 `sysbench_oltp`，不能包装成 `scheduled_single_sql` 冒充同一负载。装饰器不会抢占或强杀外部压测进程；执行超时、取消和及时恢复仍需由对应动态执行器实现。

**尚未提供完整 `tune-dynamic` 入口。** 这些保护组件和下述实机验收不是完整的多智能体动态优化闭环，不能把组件实现状态写成性能结论。

## 实机验收协议：不调用模型、不额外注入压测

```sh
python -m admtune.replay \
  --target configs/local/autodl-smoke-target.yaml \
  --scenario composition --phase-seconds 96 --guard-acceptance \
  --dedicated-instance --output runs/autodl-phase-guard-001
```

该验收仍使用单 SQL 回放，A→B→A 各 96 秒，共 288 秒。只观测已有真实请求，不修改数据库参数，也不并行运行 Sysbench。

验收的应用/恢复/提案预算为零，因为不执行这些动作；保持 15 秒预热区间与 60 秒测量区间，加一窗封存和 16 秒检测预留，单观测最小阶段为 96 秒。该设置不能直接用于真实参数变更或完整五槽搜索。

验收包含三项预声明检查：

1. 初始阶段第 8 秒就绪后，保留 15 秒预热区间、60 秒测量区间，等待覆盖终点的完整窗口，核验同阶段真实请求可接受。
2. 边界前一窗，正常长观测因时间不足被拒绝。
3. 明确标记的故意探针绕过准入，只观测边界两侧请求；必须被运行时栅栏拒绝，性能值必须为空。真实调优装饰器不暴露此绕过开关。

P95 只用于验收观测区间，不是 Sysbench TPS，也不是新的正式调优目标。所有记录标记 `gp_label_written=false`，不写代理模型训练标签。

除已有原始记录和 CSV 外，新增 `phase_guard.json`、`phase_guard.csv`，保存区间、阶段 epoch、拒绝理由、封存窗口、请求数和准入拒绝记录。自动校验和覆盖这些文件。24 秒阶段配合 `--guard-acceptance` 会在建立数据库连接和创建输出目录之前明确报错。
