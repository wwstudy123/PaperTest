## 2. 根因：特殊值与普通区间的契约不清晰

实际调用顺序是 `selector → pruner → selector → pruner`。两次selector均选择缓冲池、两个I/O容量参数、InnoDB线程并发参数。

两次pruner均返回了相同的无效并发范围：

```json
{"lower": null, "upper": null, "choices": [], "special": [0]}
```

`0`确实是允许的特殊值，但现有范围接口不支持“仅特殊值、无普通数值区间”：整数参数仍必须提供位于硬边界1～32内的普通数值上下界。旧提示强调“0放special、不扩大普通范围”，却没有明确禁止“只留特殊值并把普通区间写null”，模型两次采用了这一解释。

控制器拒绝了该范围。这是**生成格式/接口问题**，不是数据库执行异常、GP预测差或ADMTune性能劣于其他方法。重复selector不能修复pruner的具体错误，反而多花了一次调用。

## 3. 本次离线修复

1. 提示明确：整数/浮点参数即使含特殊0，也必须提供数字上下界；本接口不支持仅特殊值范围。
2. 裁剪请求附带逐参数数值契约，显式声明不允许null；不向模型预填推荐配置或收益。
3. 错误返回包含具体参数名、合法硬边界和步长，不再只有泛化报错；同时拒绝布尔值冒充数字。
4. 静态初始化已有合法参数选择但尚无合法范围时，格式重试复用该选择，只重试裁剪，不再次付费选择参数。
5. 保留最多一次格式纠错；第二次仍无效即停止。没有自动替模型补上下界、放宽硬约束或启用启发式替身。

新增3项回归测试覆盖原始错误、可操作反馈、避免重复selector，以及第二次失败仍停止。**本地223项测试全部通过。** 这些离线测试不调用付费API，不能证明下一次真实模型一定输出正确。
