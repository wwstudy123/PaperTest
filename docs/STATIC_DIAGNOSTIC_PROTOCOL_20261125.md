# 九次零模型静态诊断协议

目的：区分100分钟运行的吞吐收益来自缓冲池，还是完整配置中的其他参数；同时检查尾延迟退化与CPU配额节流、物理读取的关联。不是新的算法基线，也不是消融实验。

## 冻结配置与执行顺序

| 配置 | 缓冲池 | io_capacity | io_capacity_max | sort_buffer_size |
|---|---:|---:|---:|---:|
| Default | 1 GiB | 200 | 2000 | 256 KiB |
| BufferOnly | 4 GiB | 200 | 2000 | 256 KiB |
| ADMTuneConfig | 4 GiB | 1200 | 4500 | 256 KiB |

完整配置固定为已核验的 `timed-static-100min-002` 接受配置，不重新搜索。

使用三个位置平衡的拉丁区组，预先固定顺序：

1. Default → BufferOnly → ADMTuneConfig。
2. BufferOnly → ADMTuneConfig → Default。
3. ADMTuneConfig → Default → BufferOnly。

各配置在每个区组及每个位置各出现一次。不是随机顺序，也不是三个独立数据生成种子。

## 测量、采样与恢复

- 同一MySQL 8.0.36专用3308实例、四表各200万行；原生Sysbench只读、uniform、32线程、种子42。
- 每次15秒独立预热，加60秒正式测量；不改100分钟运行的测量协议。
- 运行前恢复不可变冷快照一次；每次测量前后恢复共同初始配置，等待缓冲池实际扩缩容完成。并非每次重启或清空所有缓存，位置平衡用于减轻顺序影响，不能保证消除所有缓存影响。
- 只围绕正式60秒命令采样，不把预热和扩缩容混入计数器差值；边界仍含少量采样及命令启动/退出开销。
- 采集MySQL进程CPU核当量、进程物理读写字节、InnoDB逻辑及物理读计数、容器CPU使用和节流计数。禁止使用宿主机全局磁盘指标冒充本实验指标。
- 校验采样进程与MySQL在同一cgroup。v1 `throttled_time`按纳秒转换，v2 `throttled_usec`按微秒转换；报告节流周期占比，不将累计节流时长除以墙钟时间冒充CPU阻塞百分比。
- 最终恢复初始配置；保存所有原始日志、边界计数器、配置回读、行数及样本哈希复核。无效观测明确标记，不补造成功记录。
- 零LLM，不调用推荐、反思或模型训练；诊断不改变原71次运行的模型与账本。

## 解释边界

- 各组分别报告三次TPS/P95观测和中位数，按同一区组计算完整配置相对BufferOnly的差值。
- 若两种4 GiB配置接近，只能说当前收益主要由缓冲池解释，不能据此宣称多智能体或GP贡献已得到证明。
- 节流与高P95同时出现仅是关联证据；证明因果还需固定请求速率或并发控制实验。不得修改OS配额后当作同条件结果。
- 固定并发下各配置实际吞吐不同，当前九次实验不等于相同到达率的延迟比较。
- 不合并本次手工配置与原ADMTune搜索最优，不挑选最好的一次替换最终复测。

入口：`python -m admtune.static_diagnostic`，需要专用实例确认、完成的冷恢复审计和原100分钟运行目录。原计时运行所在工作树保持冻结，另建诊断工作树部署，避免破坏后续72号续接条件。
