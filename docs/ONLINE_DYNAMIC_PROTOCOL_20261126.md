# 参考 OnlineTune 的只读动态实验先导

本次借鉴 OnlineTune 的工作负载组成变化、旧负载重现和全过程评价思路，**不声称复现其原始硬件、TPC-C/JOB查询或论文数值**。保留已有服务器与数据库，避免再次生成数据及迁移环境。

## 固定设置

- MySQL 8.0.36、专用3308、四表各200万行；初始缓冲池1 GiB、排序缓冲256 KiB。
- 仅调整数据库层四参数：缓冲池、排序缓冲、I/O capacity及其max。固定原生并发限制0，不改CPU配额、OS或持久性。
- 全只读范围聚合／排序聚合；R=32768、K=8192，每秒10条外生请求、4客户端工作线程，seed=42。
- A扫描/排序9:1，B为1:9，最后重现A；各600秒，总1800秒、18000条相同请求。
- 动态目标为固定到达率下端到端P95最小化，**不是静态TPS/P95，也不是标准Sysbench事务TPS**。
- 监测使用共同模板空间和独立中性归一化窗口，不把未来阶段标签输入算法。

## 分阶段执行与预算

1. 六次零LLM校准，扫描、排序分别“初始—单参数候选—初始”；每流84秒，15秒预热、60秒观测，种子710/711。收益超过5%、两侧初始漂移不超过20%时才进入付费运行。这验证参数信号，不证明两个阶段的最优配置必然相反。
2. 校准参考重复估计原始对数延迟噪声，取`max(0.02, 两组参考对的合并标准差)`，在付费运行前冻结；仅有2个重复自由度，不宣称总体校准已可靠。该固定项进入GP训练协方差，每次更新重优化；不导入校准性能标签、配置经验或最优答案。
3. Default固定初始配置跑完整A→B→A，不调用LLM。
4. ADMTune跑完全相同请求计划，最多18个配置测量槽、12次API、20000 token。每阶段基准、最多4个候选和最终复测；15+60秒测量。LLM用于选择、裁剪、批量推荐和阶段末增量反思，禁止启发式降级。未使用预算不凑数。
5. 每个独立运行前正常冷启动、禁用缓冲池dump/load；操作系统页缓存不清空。每运行后恢复初始参数并检查四表完整逻辑校验和，不复制或删除旧数据目录。

当前先做Default与ADMTune，**没有新增AgenticDB、AgentTune或OnlineTune动态基线**。若结果有价值，再加入同预算方法对比与消融；不把Default优势比较扩大为优于其他算法。

全过程图不能只画已接受最优点，不能删除参数切换或调优期间表现；异常、丢弃、队列等待和达成到达率单独报告。累计指标基于原请求流，是探索性指标，不冒充累计事务数或跨重复置信区间。
