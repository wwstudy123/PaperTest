# 论文性能对比：真实数据优先的分阶段协议

日期：2026-11-24。服务器以本轮新容器为准，不拼接旧容器的绝对性能值。

## 论文写法与本项目的区别

已核对用户提供的 AgenticDB 第 8–9 页及 AgentTune 第 14–16 页。

- AgenticDB 图 5：墙钟时间为横轴；OLTP 分别画 TPS/P95、TPS、P95，OLAP 画完整查询集耗时。
  该文使用 100 分钟墙钟上限、每次 OLTP 测量 60 秒，每方法运行三次，取最终目标中位数对应的运行。
  目标是 TPS/P95，且允许数据库后切换到 OS 调优；这些条件不能直接照搬到当前只调数据库的 ADMTune。
- AgentTune 图 8：真实 workload replay 次数为横轴，画 best-so-far 性能；
  每方法上限 100 次 replay，OLTP 最大化 TPS，OLAP 最小化完整查询耗时。
  一次树搜索迭代可能包含多次测量，不能把“迭代”直接当作一次试验。
- 当前快速先导选择 TPS 目标，与现有 ADMTune 静态控制器一致。
  同时保留 TPS 与同一配置对应的 P95；不能把两个不同配置的最优 TPS 和最低 P95 拼接成一个性能点。
  这不是复现论文数值，也不是 ADMTune 动态创新有效性的完整证据。

## 已冻结的首批先导设置

- 容器：以运行 manifest 中的 hostname、环境标识、源码版本为准。
- MySQL 8.0.36，独立实例 3308；四表各 200 万行，来自 Sysbench prepare。
- 原生 `oltp_read_only.lua`，32 并发，15 秒独立预热 + 60 秒测量，种子 42。
- 保持持久性与硬件设置不变，参数空间沿用 v2 的四个数据库参数。
- 每个方法开始前从同一冷快照恢复，并核验行数、样本、配置、快照校验和；保留替换前目录。
- Default：同一未调优配置的三次顺序测量。这不是三个独立种子，不能用于宣称跨种子置信区间。
- ADMTune：单种子，最多八个真实试验槽（含失败与最终复测），最多四次 LLM 调用、
  20000 token 全局预留预算，1800 秒墙钟上限。
- 为省钱，参数选择、范围裁剪、批量候选各调用一次；每次实测都更新 GP，
  阶段末统一归纳新增证据。最终复测占试验槽，不回填搜索最优曲线。
- 两个方法串行执行，不同方法的调参/压测不得并行干扰。

本协议使用只读负载是为了先快速形成标准 Sysbench TPS 数据，减少写入状态漂移。
后续必须扩展读写负载与动态组成变化，不能只凭静态只读结果证明动态机制有效。

## 数据源与图

每个运行保存：

1. manifest：硬件/数据/协议/空间、起始状态、冷恢复证据、源码提交及脏状态。
2. 原始 Sysbench 测量日志、逐配置 JSONL、起止耗时、应用/恢复与缓冲池就绪检查。
3. ADMTune 的试验前 GP 快照、候选筛选事件、真实 API 用量与反思证据映射。
4. `curve.csv`：逐真实槽 TPS、P95、best-so-far TPS、对应 P95、墙钟结束时刻及配置。
5. 最终复测单列，不拿搜索最高值替代最终复测，也不删除失败试验。
6. 文件校验和；绘图脚本仅接收真实、兼容且完成的运行，不补造缺失方法。

首批图必须标为 **Pilot / one seed / incomplete baseline matrix**，用于展示原始实验进展。
正式图需各方法同协议、同预算、独立种子至少三次；同时报告最终性能分布、达标试验次数、
墙钟时间与 LLM 开销。三个种子只是最低起点，若波动大还需增加重复。
方法提前停止后的常数延长只能标作“最后已知最优”，不能伪称后续时刻仍在重复测量。
