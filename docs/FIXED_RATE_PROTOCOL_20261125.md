# 固定1000 TPS延迟复验协议

承接九次无速率限制诊断，不重新搜索参数，不调用LLM。

## 预先确定的变更

- 仍用Default、BufferOnly、ADMTuneConfig三种固定配置，原三位置平衡区组顺序不变，每组3次，共9次。
- 唯一新增负载控制是原生Sysbench `--rate=1000`，同时作用于15秒预热和60秒正式测量。它是平均事务事件率，不是SQL语句数，也不是强制每次恰好完成60000个事件。
- 保持32线程、uniform、随机种子42、表规模、MySQL版本、CPU配额和其他配置不变。
- 1000低于上轮最慢Default观测1400.53 TPS；这是在本轮开始前确定的较保守负载，不用本轮结果事后挑选速率。
- 独立冷恢复一次，每次测量前后恢复共同初始配置，等待缓冲池实际扩缩容；不修改原71次调优和前轮诊断结果。
- 新增模式 `--fixed-rate 1000`，普通诊断不注入速率；拒绝重复指定速率或静默覆盖。

## 有效性与解释

1. 保存预热及测量命令的安全控制参数证据，不保存含密码的完整命令。
2. 校验原始日志的 `Target transaction rate: 1000/sec`、60秒完整测量、零错误，并要求实测TPS相对目标偏差不超过预先固定的5%；不达标则保留记录并停止，不冒充等负载成功比较。
3. 保存原生报告中的排队长度（若该版本输出），并采集与前轮相同的正式测量边界CPU、节流、物理读取指标。
4. 比较事务P95和平均延迟；TPS接近1000是施加的负载，不是性能上限，不应再声称各配置最大吞吐都是1000。
5. 原生Sysbench延迟口径保持不变；没有逐事务计划到达时间，不能将这些统计擅自称为包含全部外部调度等待的端到端SLO测量。
6. 若尾延迟与节流同时下降，只能支持“前轮问题与饱和负载有关”的解释；本试验并未单独干预CPU节流，不能声称严格证明唯一原因。
7. 仍保留全部有效及未达标观测，不替换前轮Default波动，也不把这一固定配置复验包装成算法消融。
