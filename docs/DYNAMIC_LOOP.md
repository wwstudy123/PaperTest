# 真实动态闭环试运行

## 范围与目标

`python -m admtune.dynamic` 将持续请求、阶段监测、独立调优线程、真实配置应用、同流测量、GP 预筛和增量反思接在一起。当前仅支持专用本地 MySQL 8.0.36 和无需重启的数据库参数；不修改操作系统设置，不并行注入 Sysbench。

动态目标明确为 `p95_latency_ms:minimize`：固定外生到达率下，最小化请求端到端 P95。它与此前静态 TPS 目标分开存储、建模和报告，不能把完成 QPS 固定当成调优收益。目标目录里的 benchmark 只复用表结构、实例预检等设置，不执行其中的 Sysbench 脚本。

这仍是**小预算闭环验收，不是正式基线、消融或性能优势结论**。当前数据规模、低速到达、测量稳定性和数据快照还不构成正式协议。

早期试运行见 [动态调优实机记录](DYNAMIC_RESULTS_20261123.md)：零模型控制流通过，首轮真实模型因预算预留不足停止。费用修复后的 [第二轮真实动态验收](DYNAMIC_LLM_002_20261123.md) 已完成 18000 请求、15 次实测、12 次调用/14474 token，并通过严格整轮验收；仍不是正式基线或消融。

## 并发与有效性

- 主线程独立发出预定请求，监测回调只更新短状态；SQLite 和配置变更只由一个控制线程处理。
- 阶段稳定后重新实测当前配置作为基准，随后执行选择、裁剪、候选推荐及真实试验。
- 每次观测经过阶段准入、预热、完整测量、请求排空、配置回读和完整窗口封存。跨阶段、缺窗、超时、请求失败、丢弃、旧配置会话等均不能成为有效 GP 标签。
- 公告的阶段时间表只用于各方法共同的时间预算和跨段审计，不把未来 A/B 标签输入检测器或性能模型。
- 全局参数变更后，工作连接按配置 generation 刷新，并显式应用、读回会话参数。仅 `SET GLOBAL sort_buffer_size` 不会自动更新既有连接，因此不能只看全局读回就声称生效。
- 缓冲池大小的参数读回不等于后台 resize 已完成。应用前后及恢复前后检查 resize 状态码、页记账容量和目标值，并要求两次连续空闲读回；等待有界，失败不产生性能标签。物理调整完成也不等于缓存和测量方差已经校准。
- 参数应用/恢复期间和跨配置 generation 的请求单独标记；测量区间含此类请求则拒绝性能值。
- 性能标签按 1e-6 ms 报告精度保存，同时保留未舍入 P95 及原始时间戳。此精度不是时钟准确度或测量稳定性的声明。
- 同一配置路径使用本机文件锁，拒绝第二个动态调优进程；这不是跨主机分布式锁，其他工具也必须保持专用实例互斥。
- 结束时先停止控制线程，再恢复初始配置，防止后台线程在恢复后继续修改参数。数据内容不会自动恢复。

## 预算与调用节约

每阶段最多六个真实试验槽：基准、最多四个搜索试验、最后一个复测。A→B→A 全轮最多十八个；失败不退还，无法找到可试验候选时可以少用，不强行填满。

每阶段参数选择、范围裁剪各一次，推荐一次最多六个候选；这些候选围绕阶段初始已验证父配置生成。控制器逐次实测、更新 GP、重新评估剩余候选，而不是重复付费生成同一批候选。反思在阶段完成时处理尚未消费的记录一次，并在后续阶段检索。

因此本次试运行全局上限为 **12 次实际接口请求、20000 token**，每次最大输出 1024 token，无隐式重试、无启发式降级。字节长度保守预留可能提前阻止调用，不能为完成试验绕过预算。候选池与阶段末批量反思是节约调用的明确协议，不能冒充已经实现无限预算的逐轮重采样。

`0.7.2` 将发送 JSON 紧凑序列化，新阶段清除上一阶段 GP 拒绝反馈，并将检索解释限制为带截断标记的短预览；原记录、适用条件和证据编号保留。没有降低预留公式、提高预算或丢弃反思中的执行事实；也不保证十二次请求必定在该上限内完成。

`0.7.3` 对反思证据编号作可逆短编码，保存映射并还原后按全编号校验，不删减观测。费用离线检查和下一轮协议见 [模型费用检查](PROMPT_BUDGET_20261123.md)；`reflection_maps/` 必须与模型接口记录一起归档。

新阶段基准失败时会清除旧基准、旧最优数值及 GP 拟合标志，不使用上个阶段的基准代替。本轮 GP 使用真实动态编码（四个配置维度加当前多时间片上下文），不导入旧静态五维模型。

## 执行顺序

先装依赖并通过离线测试，再在服务器执行零 LLM 软件链路验收：

```sh
python -m admtune.dynamic \
  --target configs/local/autodl-smoke-target.yaml \
  --benchmark configs/local/autodl-smoke-benchmark.yaml \
  --knobs configs/local/autodl-smoke-knobs.yaml \
  --dedicated-instance --backend heuristic --smoke \
  --phase-seconds 128 --warmup-seconds 0 --measurement-seconds 4 \
  --output runs/autodl-dynamic-smoke-002
```

这是显式的短时软件验收，不是经过校准的性能协议；启发式角色只是测试替身，不是 AgentTune、AgenticDB 基线或随机搜索基线。

零 LLM 门槛通过后，保留此前 15+60 秒时长执行真实模型试运行：

```sh
python -m admtune.dynamic \
  --target configs/local/autodl-smoke-target.yaml \
  --benchmark configs/local/autodl-smoke-benchmark.yaml \
  --knobs configs/local/autodl-smoke-knobs.yaml \
  --dedicated-instance --backend llm --allow-paid-llm \
  --phase-seconds 600 --warmup-seconds 15 --measurement-seconds 60 \
  --llm-calls 12 --llm-tokens 20000 \
  --output runs/autodl-dynamic-llm-001
```

每阶段按应用/恢复各 5 秒、封存一窗 4 秒、模型提案 30 秒、六槽计算预算下限 580 秒，选择 600 秒。该设置不允许重启参数，也不是开销已实测校准的硬实时保证；实际慢于预算则拒绝后续试验或使观测失效。

每轮约三十分钟固定时间表；不因为某方法或模型调用变慢而延长负载阶段。独立重复前的数据快照复位仍是正式实验前置门槛，本入口不会默默复位数据。

## 通过条件与记录

不能仅以程序退出或请求发出完成判断闭环成功。`control_flow_completed` 要求三个阶段都有有效基准和复测；每阶段执行过有效候选，或有明确的“剩余新候选全部被 GP 拒绝”事件；全轮至少执行过一个有效候选，GP 实际执行过预筛且至少有一次试验前预测与实测；三次反思均通过证据校验，最终还须校验请求完整性与恢复。

`closed_loop_completed` 保留更早的“每阶段都必须执行有效候选”严格判定，不会覆写旧结果。`gp_selected_execution_exercised` 单独表示是否确实实测过 GP 选出的搜索配置，不能拿已选配置的复测代替。旧负载重现时保守拒绝新候选是合法分支，不强行绕过置信准入来凑数量。

原 `smoke-001` 的严格验收结果保持失败记录，不改写。新的验收契约标记为 `control_flow_v2_resize_stable`，只是明确区分控制流完整性、额外搜索路径覆盖和性能效果；没有降低配置、阶段、请求或恢复的有效性要求。

复测前也保存预测，之后再将有效复测用于后续拟合和噪声估计。该预测是“已选配置的重复观测”，不是独立未见配置测试；搜索候选与复测的预测计数分别报告。如果 GP 判断没有可安全试验的新候选，不为凑预测数据而绕过置信准入。

记录包括：

- 原有计划、逐请求/窗口 JSONL，以及请求、模板率和阶段事件 CSV。
- `records.sqlite3`、`trials.jsonl`、`dynamic_trials.csv`：配置、目标值、预测、接受/恢复、区间及 generation。
- `gp_models/gp-*.json`：每次拟合的训练编号、完整输入/标签、归一化、核、实际超参数、优化器状态和版本；`GaussianProcess.from_snapshot()` 可固定参数重建预测。
- `llm_calls/` 与 `llm_usage.json`：逐角色提示/响应、真实用量，不保存密钥。
- `progress.json`、`dynamic_summary.json`、`summary.json`：实时进展、各阶段结果、全局预算、恢复状态及是否通过严格门槛。

原始产物由 Git 忽略。反思现在包含配置、阶段与试验类型上下文，避免把同配置复测的波动误解释成配置空间差异；输出文字仍是待验证解释，不自动视为因果规律。
