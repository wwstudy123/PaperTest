# 统一范围扫描与排序的动态验收协议

日期：2026-11-24。此阶段只验证监测、阶段保护及记录，不调用 LLM，不调参，不写入 GP 训练标签。

## 为什么需要单独接通

此前范围扫描与排序各自建立模板集合，两个独立的“全读”上下文不能直接用于区分 SQL 组成变化。
本次使用预声明的共同模板集合：四张表各有范围聚合、排序后聚合两类 SQL，共八个模板。
模板聚类、归一化和阈值仅依赖独立的中性校准窗口，不读取未来计划或阶段标签。

## 固定设置

- 隔离实例 3308，`admtune_workset_v2_full`，四表各 200 万行。
- 范围行数 R=32768，排序 K=8192，SQL 与已验证的固定负载筛查一致。
- 全部只读，10 QPS，四个工作线程，队列上限 32；QPS 不是 Sysbench 事务 TPS。
- `range-mixed` + `composition`：每秒扫描/排序比例 9:1 → 1:9 → 9:1。
- 每阶段 96 秒，共 288 秒、2880 条计划请求，默认种子 42。
- 对照为同一模板空间下 `steady` 的固定 1:1，每阶段占位时长 24 秒，共 72 秒、720 条请求。
- 窗口 4 秒、两个时间片；沿用联调阈值，不以此宣称正式校准完成。
- 正常同阶段观测保留 15 秒预热、60 秒测量；尾部试验必须拒绝，
  故意跨阶段探针必须失效，不能写入模型。
- 起止配置须相同。只读 SQL 不要求本轮再次冷恢复；这不等于独立性能重复已执行快照复位。

## 命令

```bash
python -m admtune.replay --target configs/local/workset-v2-target.yaml \
  --output runs/NAME --scenario composition --phase-seconds 96 \
  --query-profile range-mixed --table-size 2000000 --range-rows 32768 --top-k 8192 \
  --guard-acceptance --dedicated-instance
```

固定组成对照使用 `--scenario steady --phase-seconds 24`，省略 `--guard-acceptance`。

动态调优入口也增加相同的 `--query-profile range-mixed --range-rows 32768 --top-k 8192`，
但本阶段不启动该入口或付费搜索。上下文兼容键增加模板、校准和查询定义，拒绝将旧点查询空间混作相同模型输入。
运行诊断不再把范围排序描述为“不含排序的点查询”，同时记录观测到的排序比例。

## 通过标准与解释边界

1. 所有请求成功，无丢弃、SQL 异常或超限发射延迟。
2. 动态场景只确认三个阶段；固定组成对照只确认一个阶段。
3. 两类 SQL 通道不同，均非未知模板；请求记录保留 R、K、聚合计数和结果指纹。
4. 同阶段观测可封存，尾部准入拒绝，跨阶段探针拒绝，GP 标签数为零。
5. 配置起止一致，保存原始 JSON/JSONL、绘图 CSV 与校验和。

通过仅代表此负载协议的真实监测与保护验收，不代表 ADMTune 优于基线，
不代表 GP 已训练可靠，也不替代跨运行恢复、独立种子重复及正式基线/消融。
